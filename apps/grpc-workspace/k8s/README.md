# Kubernetes

Generated by `setu generate app` or `setu adopt` — one Deployment and one Service per member,
regenerated whenever a member is added.

## Deploy

```bash
npx @setu-ts/cli@0.12.0 workspace deploy --dry-run   # show the plan
npx @setu-ts/cli@0.12.0 workspace deploy             # build, ship, apply, wait
```

It builds every member's image, tags it with the current commit, loads it into a `kind-*` context's
cluster or pushes it to `--registry` for any other context, applies one Secret per member, applies
this file with the namespace and images filled in, and waits for every rollout. Flags: `--context`,
`--namespace` (default: the workspace directory name), `--registry`, `--tag`, `--timeout` (default
`120s`), `--build-arg`, `--network`, and `--pull-secret <name>` (repeatable; an existing registry
Secret in the namespace).

**Secrets.** A member's variables are the names its committed `.env.example` declares; their values
go in `k8s/secrets/<member>/.env`, which git ignores and no image copies. Deploy refuses, naming
every missing variable, before it builds anything, and sends the values to `kubectl` on stdin. Each
Deployment reads its Secret, `<member>-env`, through `envFrom`, and its Secret version is stamped
into the pod template, so a changed Secret rolls it out. For production, keep the values in a secret
manager (Sealed Secrets, External Secrets) and create the same Secret from it.

**By hand.** `${NAMESPACE}` and `${WORKSPACE}` are placeholders, not shell variables: fill them in,
or pipe the file through `envsubst`:

```bash
NAMESPACE=acme WORKSPACE=acme envsubst < k8s/members.yaml | kubectl apply -f -
```

Probes follow DECLARED health support. A member generated WITH a template, or adopted from a project
that declares `@setu-ts/health-plugin` or a starter, is recorded in `setu.workspace.json` with
`healthProbes: true` and gets `httpGet` probes on `/live` and `/ready`. A member with no such
declaration keeps a `tcpSocket` probe, because pointing one at a 404 would make it permanently
unready. The declaration is a dependency, not proof that the plugin is registered — if the config
never registers it, or it uses custom endpoints, edit the probe paths.

Members recorded with `metricsEndpoint: true` carry Prometheus discovery annotations —
`prometheus.io/scrape: 'true'`, `prometheus.io/port: <the member's port>`, and
`prometheus.io/path: /metrics` — so a Prometheus scraping the standard annotations finds every
member without static target config. Members without that record carry none, because annotating a
member that serves no `/metrics` would make Prometheus report a permanently-down target.

What this does NOT include, deliberately:

- **An Ingress.** Which controller, which host, and which TLS issuer are cluster decisions, and a
  guessed Ingress is one that silently routes nothing.
- **The transport's backing service.** This workspace needs none.
- **HTTP probes** for a member with no declared health support. A member recorded with
  `healthProbes` serves `/live` and `/ready`, so its probes are `httpGet`; one without keeps a
  `tcpSocket` probe, because pointing a probe at a 404 would make it permanently unready. A
  dependency does not prove registration, and custom endpoints need edited paths.
- **A discovery backend.** These objects make each member reachable by its Service name, which is
  what the generated map's `<MEMBER>_HOST` variables are set to here. For anything beyond a fixed
  list, use the plugin's `kubernetes` provider — it needs the RBAC documented in this repository's
  deployment guide.
