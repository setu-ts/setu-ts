# Milestone 111e3 — CI, apps and website on Node; root Deno manifest removed

> **Status:** Planning. Branch: `feat/m111e3-node-ci`. `develop` and `main` are protected — all work
> (implementation + fixes) stays on this one branch until it merges via a single PR into `develop`.

## 0. Objective & scope

M111e1 and M111e2 moved formatting, linting, scripts and root tests to Node, but kept every
`deno task` name working by forwarding it to `pnpm run`, so the root `deno.json` and `deno.lock`
still exist and CI still installs Deno for every job. This milestone removes them. After it, the
repository is built, checked, tested, released and deployed with Node 24 and pnpm. Deno remains a
**supported runtime**, not repository tooling: the `packages/runtime` Deno adapter, the CLI's
`--runtime deno` projects, the local diagnostics connector (Deno-only by design, M98b) and the
Deno-lane proofs keep a Deno binary, in one CI job that installs Deno only for them.

One milestone, one PR (maintainer decision, 2026-10-15).

- **In scope:**
  - Delete the root `deno.json` and `deno.lock`. The workspace member list moves to an authored
    `pnpm-workspace.yaml`, read by one helper.
  - Every repository command becomes `pnpm run <name>` (or `pnpm <name>`). No `deno task` forwarding
    remains.
  - The Deno lane gets its own generated configuration and lockfile under `test/deno-lane/`.
  - CI (`ci.yml`, `release.yml`, `drift.yml`, `website.yml`) runs on `actions/setup-node` + pnpm.
    Deno is installed only where a Deno runtime is the subject (§3.5): the lane, the CLI's
    Deno-target e2e, the SDK fixture format check, the Deno-target deploy scaffold and the
    view-plugin resolution check.
  - `pnpm-lock.yaml` replaces `deno.lock` as the input to the resolved-set release artifact, the
    dependency-drift report and the vulnerability audit.
  - The 17 `apps/*` examples become pnpm workspace members, run on Node through `tsx`, and
    `check:apps` runs them that way.
  - `apps/compiled-binary` moves from `deno compile` to a Node single executable application (SEA),
    decided by the probe recorded in §1.
  - The two Docker images move from `denoland/deno` to Node.
  - The website moves to pnpm (its own lockfile), Node test running and the root Prettier/ESLint
    config; its API reference is generated by TypeDoc HTML (maintainer decision, 2026-10-15).
  - The four Deno users M111e2 left (`test/node/task-surface.test.ts`): `docs:api`'s
    `deno doc --html`, the `check:browser` harness, `test/fixtures/contract-ast.ts`'s
    `deno doc --json`, and `CHECK_EXCLUDED_UNTIL_APPS_MOVE`.
  - `deno-view-plugin-resolution` in CI resolves the published npm package from a Deno project
    instead of JSR.
  - The command blocks that become unrunnable (CLAUDE.md "Verification", `docs/releasing.md`) — see
    C1.
- **NOT this milestone:**
  - Hand-written prose that still says `deno task`, `jsr:@setu-ts` or "Deno-first" across
    `AI_GUIDELINES.md`, `ARCHITECTURE.md`, package READMEs, `docs/` and `CHANGELOG.md` history —
    **M111f** (its exit criterion is exactly that search). This milestone changes only the command
    blocks that stop working (C1) and generated text.
  - Generated output for Deno-target projects (`packages/cli` emits `deno task …` for
    `--runtime deno`): correct and unchanged.
  - Vite+ / Oxlint / TypeScript 7 — deferred by the maintainer to mid-December 2026.
  - Repairing the Cloudflare Workers Builds dashboard settings: a maintainer action. This milestone
    makes the website build self-contained (§3.9), which is what the dashboard needs.

## 3. Design decisions

### 3.1 The workspace member list

- **Decision:** `pnpm-workspace.yaml` becomes the authored source. It lists the framework members
  explicitly (the existing 52 entries) and the apps with the glob `apps/*` (website stays out,
  §3.9). One internal helper, `scripts/lib/workspace.ts`, exports
  `workspaceMembers(): Promise<string[]>` (framework members only — entries under `packages/`) and
  `workspaceApps(): Promise<string[]>` (the expanded `apps/*` directories), parsing the file with
  `yaml@2.9.1`, pinned as a root devDependency at the version already in the lockfile. All seven
  readers in §1 call it; none parses `deno.json` for the list any more. `node-manifests.ts` stops
  generating `pnpm-workspace.yaml` and instead checks that every entry has a member `deno.json`.
  `release:verify`'s whole-workspace coverage check reads `workspaceMembers()`, so apps never need a
  release-list entry.
- **Why:** pnpm already reads this file; a second list would drift. Splitting members from apps
  keeps every release and manifest script on the published set.
- **Test home:** `test/node/workspace.test.ts` (parse, split, missing file, an entry with no
  `deno.json`), plus each reader's existing test re-pointed at a fixture `pnpm-workspace.yaml`.

### 3.2 Root `deno.json` / `deno.lock` removal and the command surface

- **Decision:** both files are deleted. Every CI step, script and runnable doc block calls
  `pnpm run <name>`. No script is renamed: `pnpm test` / `pnpm test:coverage` already run the
  package suites, so a `deno task test` / `deno task test:coverage` (which forwarded to the root
  tooling suite) becomes `pnpm run test:tooling` / `pnpm run test:tooling:coverage`.
  `test/node/task-surface.test.ts` is rewritten to pin the new state: no root
  `deno.json`/`deno.lock`; the only `package.json` scripts containing `deno ` are `test:deno-lane`
  and `fmt`/`fmt:check` (the SDK fixtures, §3.11); the only scripts spawning `deno` are
  `test-deno-lane.ts`, `inspect-local-diagnostics.ts` and `check-deploy.ts`'s Deno-target scaffold
  step; no root fixture spawns `deno`.
- **Why:** the forwarding layer existed only to keep names stable during the move.
- **Test home:** `test/node/task-surface.test.ts`.

### 3.3 The Deno lane

- **Decision:** `scripts/node-manifests.ts` generates `test/deno-lane/lane.config.json` from the
  member manifests (compiler options from `tsconfig.base.json`'s checked subset plus the Deno libs;
  the imports and scopes of the hand-written `test/deno-lane/deno.json`, which also receives the
  root `deno.json` `imports` the lane needs before that file is deleted; one `@setu-ts/*` mapping
  per member export; `nodeModulesDir: "auto"`), and `--check` refuses drift.
  `test/deno-lane/deno.lock` is committed and the lane runs `--frozen`;
  `test/deno-lane/node_modules/` is gitignored.
  - **Permissions:** the generated config also carries one named permission set per member that owns
    lane tests, copied verbatim from that member's `deno.json` `test.permissions` (today: cli,
    diagnostics-plugin, realtime-backplane-plugin, runtime, websocket-plugin). The driver groups
    `DENO_LANE_TESTS` by owning member and runs one `deno test -P=<member>` per group; root `test/`
    files run in one further group with today's explicit flags and no `-P`. Every group writes to
    the same `coverage-deno-lane` directory (each run adds profiles), each group gets its own JUnit
    file, and the existing per-file coverage gate reads the combined report. A single merged grant
    is rejected: it would widen loopback-only members to `net: true`, and some tests rely on a
    narrow grant refusing an address (the M53 lesson).
  - **Preparation:** before the first group the driver runs
    `deno install --config test/deno-lane/lane.config.json --frozen --entrypoint <spawned modules>`,
    where the spawned modules are every module a lane test starts as a subprocess (today only
    `scripts/inspect-local-diagnostics.ts`), and the lane lock covers their graph. A spawned module
    is not imported by any test, so nothing else puts its packages in `node_modules`; in a cold
    checkout its child printed ~500 `Initialize …` lines and failed the diagnostics stderr assertion
    (89/490), while warm runs passed only because other groups had installed the same packages
    first. A bare `deno install` is NOT the fix: it installs every import-map entry and the frozen
    lock refuses it.
  - **Discovery:** every repository-owned Deno invocation — the driver's `check`/`test` and the
    `deno run` that `test/inspect-local-diagnostics.test.ts` spawns — passes
    `--config test/deno-lane/lane.config.json` and runs with `DENO_NO_PACKAGE_JSON=1`, so Deno never
    treats the root `package.json` `workspaces` field as a Deno workspace. The driver sets the
    variable in its child environment; the inspect test adds `--config` to its spawn (the variable
    reaches it by inheritance).
- **Why:** measured in §1 — the lane needs its own mappings, the members' own permission scopes and
  a writable `node_modules`, and a committed lock keeps it reproducible. The bar is the baseline:
  **90 passed (491 steps)**.
- **Test home:** `test/unit/node-manifests.test.ts` (generated config equals the committed one,
  including one permission set per lane member equal to its `test.permissions`; a removed export is
  reported), `test/unit/deno-lane-coverage.test.ts` (one invocation per member with `-P=<member>`,
  root group without `-P`, `--config` on every invocation, the `DENO_NO_PACKAGE_JSON` variable in

### 3.7 Apps on pnpm and Node

- **Decision:**
  - Each app replaces `deno.json`/`deno.lock` with a private `package.json`: `@setu-ts/*` deps as
    `workspace:^`, npm deps as before, scripts `start`/`smoke` (and `test` where one existed) as
    `tsx main.ts` / `tsx smoke.ts`, with `tsx` a regular `dependency` of each app (it is how the app
    runs, including in its image, §3.12), plus `check` as `tsc -p tsconfig.json --noEmit`. App
    type-checking is configured by two generated files, both written by `scripts/node-manifests.ts`
    and refused on drift by `--check`:
    - a root `tsconfig.apps.json`: extends `tsconfig.base.json`; `noEmit`; `composite`,
      `declaration`, `declarationMap` and `isolatedDeclarations` off; `allowImportingTsExtensions`;
      `rewriteRelativeImportExtensions: false` (apps never emit, and the base option rejects a
      `.ts`-suffixed non-relative alias import with TS2877);
      `typeRoots: ["./node_modules/@types", "./packages/runtime/node_modules/@types"]` with
      `types: ["node", "deno"]` (typeRoots resolve relative to the config that declares them, so
      they work from any app; a relative path inside `types` does not, TS2688; and `deno` is
      required because `@setu-ts/runtime`'s source references the `Deno` global — with
      `types: ["node"]` alone an app importing it fails with 6 errors, measured); and the same
      `@setu-ts/*` `paths` mapping `tsconfig.check.json` uses, produced by the same generator
      function so the two cannot drift;
    - each app's `tsconfig.json`: `extends: "../../tsconfig.apps.json"` plus its `include`. Per-app
      overrides are data in the generator; today exactly one: `full-stack` adds `jsx: "react-jsx"`
      and must restate the FULL `paths` (the `@setu-ts` mapping rebased one level plus `~/*`),
      because `paths` replaces rather than merges through `extends`. Extending `tsconfig.check.json`
      directly was rejected by measurement: its `types` entry
      `./packages/runtime/node_modules/@types/deno` fails TS2688 from an app directory, and its
      `jsxImportSource: hono/jsx` is wrong for full-stack's React routes.
  - Apps resolve `@setu-ts/*` to workspace SOURCE through ONE mechanism: `tsx` honours the generated
    app `tsconfig.json` `paths` (measured, §1), so an app runs HEAD source without a `tsc -b` first
    (M37's "drift means HEAD"). `check:apps` does NOT also pass the source-redirect register; that
    register stays (moved to `scripts/lib/source-register.ts`) for the test subprocesses that
    already use it. Two mechanisms for one resolution would let one hide the other's defect — which
    is exactly what run 5's control showed.
  - `Deno.*` calls in app code become Node equivalents (`process.argv`, `process.on('SIGTERM')`,
    `node:child_process`, `node:fs/promises`), or go through `IRuntimeServices` where the app
    already has one.
  - `check-apps.ts` keeps the exit-77 skip, `ALLOW_SKIP`, and malformed-app reporting, now keyed on
    `package.json`.
  - `apps/full-stack` drops `nodeModulesDir` and its Deno install step; its build is
    `pnpm --filter … build`.
  - `tsx` and the sync `registerHooks` register compose on Node 24 (measured, §1), so no loader
    decision remains open.
- **Why:** the apps are the runnable proof; they must run the toolchain users run.
- **Test home:** `test/apps-gate.test.ts` (every app has `package.json`, a `smoke` script and `tsx`
  as a dependency; no app has `deno.json`; `full-stack` not in `ALLOW_SKIP`; malformed-app and

## 8. Risks & mitigations

- The CLI's Deno-target e2e spawn `deno` inside scaffolds under `.tmp/`, below the root
  `package.json`, so the same discovery warning (§1) can reach their stderr or resolution → the full
  `pnpm test` run is the measurement; where it does, the spawn environment gets
  `DENO_NO_PACKAGE_JSON=1`, never a relaxed assertion.
- An app that resolved `@setu-ts/*` to source locally runs against `dist/` in its image → the image
  path is exercised by `check:deploy` (and the cold-state run), not only by `check:apps`.
- App `Deno.*` replacements change meaning (M111e2 lesson: each replaced runtime call checked for
  meaning) → the review checks each replaced call; each app's smoke is the behavioural proof.
- A warm `dist/` or `node_modules` hides a resolution defect (M111e2's `tsc` paths trap) → the
  cold-state run in §6 is mandatory evidence.
- The renamed required check blocks merge until rulesets change → C6 pre-merge step; the PR body
  says so first.
- `pnpm audit`'s advisory source differs from `deno audit`'s, so findings may differ → the first CI
