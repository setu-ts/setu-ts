## 3. Design decisions

### 3.1 Every corrected statement comes from the cited code

- **Decision:** Each item in §5's table carries its correct text source (file:line). The implementer
  writes the new text from that code and nothing else. An item whose code does not settle the
  wording is reported, not guessed. Option names, flags, error class names and file names are copied
  from the code; the reviewer greps each against the source.
- **Why:** a hosted model that is asked to fill a gap writes plausible names (M113g lesson: 5 of 7
  invented option names). Supplying the source and checking every name closes that.
- **Test home:** the docs-claims pass on the branch (§7) and `pnpm run check:docs`.

### 3.2 Runtime messages and agent rules change with their tests

- **Decision:** Five source strings change, with the tests that assert them updated in the same
  commit:
  1. The `SessionSecretMissingError` message (`secret-resolver.ts:75-78`) names all four sources in
     order: `SessionPlugin({ secret })`, a secrets provider, configuration, the environment
     variable.
  2. The decorator-plugin error at `decorator-plugin.ts:272-273` gives the standard-decorators
     reason: TC39 decorators carry no parameter type information, so `@Inject` names the token. It
     no longer says "which Deno does not support".
  3. The agent rule at `packages/cli/src/agents/rules.ts:94` says the default applies only to an
     absent key, and to use `config.get(key) || fallback` where an empty value means unset.
  4. `rules.ts` gains a `cloudflare-workers` test rule matching the generated Workers test
     (`project-files.ts:2318-2333`, `schematics/test-harness.ts:55-62`): `node:test` and
     `node:assert` under `tsx --test`; start the Worker with `startTestServer()` from
     `test/support/server.ts`, request `server.baseUrl + path` with `fetch`, and
     `await server.stop()` in `finally`. A Workers test does not use `createTestApp`.
  5. JSDoc-only corrections, which change no behaviour: `secret-resolver.ts:16, 27`,
     `auth-plugin/src/interfaces/index.ts:44` (`privateKey`), `websocket-plugin.ts:69-71` (`@throws`
     gains `maxMessageBytes`), the `SsePlugin` and `SseService` JSDoc (`@throws` for `heartbeatMs`),
     `decorator-plugin/src/decorators/injection.ts:73-75`,
     `packages/cli/src/commands/add.ts:1851-1853` (framework packages are exempt from the 24-hour
     age), and the `createFullStackAppFromConfig` example (`from-config.ts:137-147`, see §5).
- **Why:** these say the same wrong thing as the prose. Fixing only the prose leaves an error
  message a user reads at the moment it matters still wrong.
- **Test home:** the existing assertions on each message (located by grepping the old text in
  `test/`), updated; `pnpm run check` for JSDoc; the `scaffold-runs-e2e` `agents --check` cases for
  `rules.ts`.

### 3.3 `docs/upgrading.md` records what a user's code or command meets

- **Decision:** Add short Unreleased subsections for behaviour a user's own code or a CLI command
  now meets:
  - **M140a additions:** gateways refuse HTTP authorization decorators (use
    `@Gateway(path, { guards })`); session-secret precedence (configuration before the environment,
    and `configFallback: false` no longer applies); invalid `maxMessageBytes` and `heartbeatMs` now
    throw; generated `--down` reverses one migration.
  - **A new M140b subsection:** `setu add queue` is refused on Workers, with the route to use
    instead; an empty `PORT`, broker, Redis or discovery value falls back to the default; Workers
    projects carry no `deno.json`.
  - **A new M140d subsection:** generated event type names are PascalCase; `g schema` writes
    `z.strictObject({})`; the devtool `dev` script changed.
  - **M140c additions:** images and new `start` scripts set `NODE_ENV=production`; regenerated
    Compose files add healthchecks and `depends_on`; broker defaults move to a ConfigMap listed
    before the Secret.

  No hand-edit recipes for older manifests (`deno.json` task rewrites and the like).

- **Why:** there are no projects from older CLI versions to migrate (maintainer, 2026-10-29), but a
  library behaviour change still breaks code being written against the previous release.
- **Test home:** the docs-claims pass (§7) checks each sentence against the code.

### 3.4 The run-budget recipe (V12-8)

- **Decision:** Add a recipe to `docs/durable-runs.md`, after the `model(run)` paragraph (around
  76-77), that budgets a run by its server-owned identity. It wraps the run's model with an AI SDK
  middleware that:
  - builds the quota key from `run.tenantId`, refusing a tenant-less run (`tenantId === ''`) with a
    named error;
  - calls `quota.reserve(key, estimate)` before the call, then `settle` with the actual usage, or
    `release` on failure;
  - resolves its dependencies from `run.services`, never from a request.

  The fence is a complete module that the guide fence compiler type-checks. The README line at
  `packages/agent-runs-plugin/README.md:85-86` links to it.

- **Why:** the docs tell readers to budget inside `model(run)`, but the only budget recipe needs an
  `IRequestContext`, which a run does not have. The recipe uses only the surfaces in §1.
- **Test home:** `test/guide-fence-compiler.test.ts` compiles the fence; `check:docs`.

### 3.5 The sign-out recipe (V12-88's lever)

- **Decision:** The auth-plugin README's "In the full-stack template" section (`README.md:971-1089`)
  gains sign-out. The account service adds `signOut(): void`, implemented as
  `ctx.services.get<IAuthSessionService>(CAPABILITIES.AUTH_SESSION).signOut(ctx)`. A form action
  calls it through `getService(context, ACCOUNT).signOut()`, with the hidden `_csrf` field, and
  answers a 303 redirect. One sentence names the shipped alternative: with `signIn.providers: []`, a
  plain `<form method="post" action="/auth/logout">` with the CSRF field posts to the built-in
  route. The template itself stays without sign-out, as the ROADMAP says.
- **Why:** it uses the same request-bound module service as the recipe's sign-in, so the application
  has one pattern to follow.
- **Test home:** the README fence compiler compiles the changed fence.

### 3.6 Who writes what

- **Decision:** opencode with DeepSeek free
  (`opencode run --standalone --auto -m opencode/deepseek-v4.1-flash-free`) implements, in three
  batches with self-contained briefs:
  - **Batch 1, CLI docs:** `docs/cli.md`, `packages/cli/README.md`, the CLI rows of `PUBLIC_API.md`,
    `docs/mcp.md`, `docs/react-router-dev.md`, `docs/examples.md`, `docs/deployment.md`,
    `docs/messaging-emulators.md`.
  - **Batch 2, package docs and recipes:** the plugin READMEs and cards; `docs/durable-runs.md`,
    `docs/ai.md`, `docs/retrieval.md`, `docs/decorators.md`, `docs/migration-nestjs.md`,
    `docs/plugins.md`, `docs/custom-plugins.md`; the §3.4 and §3.5 recipes; the vector-store cast
    removals (README, `docs/retrieval.md`, `apps/semantic-search`, the conformance test).
  - **Batch 3, source strings and changelog:** §3.2's source strings and their tests; CHANGELOG (C2,
    C3, and the M140e entry); `docs/upgrading.md` (§3.3).

  If a run stops on a usage limit ("Free usage limit reached" in the log), Codex resumes that batch
  from `git status` and the brief (maintainer, 2026-11-16). Claude reviews each batch's diff against
  this plan, greps every name it wrote against the source, and makes small corrections inline.

- **Why:** the maintainer's split. Most of the work is settled prose; the recipes are specified in
  §3.4 and §3.5 tightly enough to be written to the decision.
- **Test home:** §7's gates after each batch, in the scoped form below.

## 7. Verification gates

Scoped to what each batch touches (maintainer rule, 2026-11-16), with one full pass at the end:

```bash
git branch --show-current   # feat/m140e-documentation, never develop or main
pnpm run check:plan        # this plan lints clean
pnpm run fmt:check
pnpm run lint
pnpm run check
pnpm run check:docs                      # after every batch
pnpm run ci:local --shard tooling        # fence compilers, after batches 2 and 3
pnpm test:coverage session-plugin decorator-plugin --no-tooling   # batch 3's message changes
pnpm run ci:local --shard cli            # batch 3's rules.ts and env-header change, once at the end
pnpm run release:publish --dry-run       # once, on the final tree
pnpm run release:verify 0.12.0
```

After the last batch, a code review and a docs-claims pass run on the branch. Every changed sentence
is checked against the code once more before the PR. No security audit: the changes are
documentation, JSDoc, two message strings and agent rules, and no trust boundary moves. No scaffold
boot beyond `scaffold-runs-e2e`: generated code is unchanged except the env-file header comment and
the agent brief.

## 8. Risks & mitigations

- A model writes a plausible but wrong option, flag or class name → §3.1: every name is copied from
  cited source, and the reviewer greps each one against the source before accepting a batch.
- A batch stops on a usage limit with edits half-applied → check the log tail for "Free usage limit
  reached" and `git status` after every run; Codex or Claude finishes from there.
- A recipe fence type-checks but teaches a wrong pattern → §3.4 and §3.5 fix the APIs and the order
  of calls; the review reads the recipe against `quota.ts` and `auth-session.ts`, not only the
  compiler.
- Doc lines moved since the findings were recorded → each item quotes its old text; the implementer
  searches for the text, not the line number.
- `PUBLIC_API.md` tables are wide and hand-wrapping breaks them → edit cell text only and run
  `pnpm run fmt`; never re-wrap a table by hand.
